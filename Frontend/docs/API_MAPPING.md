# Daymark API Mapping & Specification

This document maps the mobile client features to the Spring Boot backend REST endpoints, their request/response structures, and authentication. Checked against the code on 2026-11-27. The client's paths are in `lib/data/network/api/api_endpoints.dart`; interactive docs are at `/swagger-ui.html` on a running backend.

## Authentication (SEC-01 / SEC-02)
- `POST /auth/login` and `POST /auth/create-user` return a JWT access token (`accessToken`, HS256, valid 7 days, `expiresAt` as an ISO-8601 instant). They never need a token and ignore one if sent.
- Every other route takes `Authorization: Bearer <accessToken>`. The app keeps the token in the platform keystore (`TokenStore`, never SharedPreferences or logs) and `AuthInterceptor` adds it to every request.
- With a token, the user comes from the token. A `userId` / user `id` the client still sends is only checked against it: a different id is a 404. By-id routes (a note, task or reminder id) only find the caller's own items; anyone else's is a 404.
- `AUTH_ENFORCED` (server env, default `false`): while false, requests **without** a token still work as before (the user is the `userId` they send) for app builds older than SEC-02. When true, every data route needs a valid token. An invalid or expired token is a 401 in both modes.
- On a 401 for a request sent with the current token, the app signs out once (`SessionService.expire`) and keeps unsynced changes for the next sign-in. A 401 from login means wrong credentials.
- Swagger UI and `/v3/api-docs` are public.

| **User Registration** | `POST` | `/auth/create-user` | `SignupRequestDto` `{name, email, password, mobile, gender}` | `ApiResponse<SignupResponseDto>` `{userId, accessToken, expiresAt}` | Public | Email is trimmed and lower-cased; 409 if already used; 400 on invalid input |

| **Change Password** | `PUT` | `/auth/change-password` | `ChangePasswordRequestDto` `{userId, oldPassword, newPassword}` | `ApiResponse<Boolean>` | Bearer | 400 if the old password is wrong. Not called from the UI yet |

| **Reminders By Date** | `GET` | `/reminders/get-by-date` | Query: `?userId={userId}&date={YYYY-MM-DD}` | `ApiResponse<List<ReminderModel>>` | Bearer | Reminders whose `dueDate` is that day |
| **Update Reminder** | `PUT` | `/reminders/update-reminder` | `UpdateReminderRequestDto` `{reminderId, title?, remindAt?, dueDate?, dueTime?, category?, status?, repeatInterval?, startAt?, lastOutcome?, lastOutcomeAt?}` | `ApiResponse<ReminderModel>` | Bearer | Partial update. | **Set Reminder Status** | `PUT` | `/reminders/update-status` | Query: `?reminderId={id}&status={status, optional}` | `ApiResponse<ReminderModel>` | Bearer | Sets `status`; without it, toggles COMPLETED ↔ PENDING |
| **Answer Reminder Occurrence** | `PUT` | `/reminders/complete-occurrence` | `CompleteOccurrenceRequestDto` `{reminderId, occurrence, outcome: COMPLETED\|MISSED}` | `ApiResponse<ReminderModel>` | Bearer | One-off: `status = outcome`. | **Delete Reminder** | `DELETE` | `/reminders/delete-reminder` | Query: `?reminderId={id}` (or `?id=`) | `ApiResponse<Boolean>` | Bearer | 404 if it doesn't exist |

## Data Model Conventions
- **Note IDs**: Numeric (`long` in Java, `int` in Dart).
- **User IDs**: Numeric (`long` in Java, `int` in Dart).
- **Timestamps (`createdAt`, `updatedAt`, `exportedAt`)**: absolute instants, ISO-8601 in UTC, e.g. `2026-11-25T20:00:00.123Z` (server: `Timestamps.now()`; app: `DateKeys.nowUtc()`). Values without an offset were written before BE-02 by a server running in UTC; they are read as UTC and never rewritten.
- **Wall-clock values (task `dueDate`/`dueTime`, reminder `remindAt`/`dueDate`/`dueTime`)**: the date and time the user picked, with no zone. They are stored and shown as is and never converted, so "9:00 on Nov 26" stays 9:00 on Nov 26 wherever the user is.
- **Date Grouping**: notes by `createdAt` (never `updatedAt`), converted to the viewer's zone first: the app uses `DateKeys.localDay`, the server uses the `tz` query parameter (an IANA name such as `Asia/Kolkata`; UTC when absent; an unknown name is a 400). Tasks go on their `dueDate`, or on the local day of `createdAt` when they have none; reminders on their `dueDate`, else the date part of `remindAt`.
- **Enumerations** (case-insensitive on input, upper case on output; anything else is a 400): `status` PENDING / COMPLETED / REJECTED / MISSED; `repeatInterval` NONE / DAILY / WEEKLY / MONTHLY; `priority` LOW / MEDIUM / HIGH; reminder `lastOutcome` / occurrence `outcome` COMPLETED / MISSED.
- **Wall-clock formats** (a 400 otherwise): `remindAt`, `startAt`, `occurrence`, `lastOutcomeAt` are `yyyy-MM-ddTHH:mm[:ss]` and are returned as `yyyy-MM-ddTHH:mm:ss`; `dueDate` is `yyyy-MM-dd`; `dueTime` is `HH:mm`.
- **Repeating reminders**: `startAt` is the first occurrence and the anchor of the series; `remindAt` is always the next pending occurrence. Monthly repeats keep `startAt`'s day of month, clamped to shorter months (Jan 31 → Feb 28 → Mar 31).
- **Response Structure**: Unified envelope `ApiResponse<T>` with `boolean success`, `String message`, and `T data`.
- **Status codes** (BE-03): 200 (201 for a new task or reminder), 400 invalid input, 401 missing/invalid/expired token or wrong credentials, 404 not found or not the caller's, 409 conflict (email in use), 429 too many login attempts, 500 with a generic message (never exception text). Errors use the same envelope with `success: false`; the app turns them into short messages with `userMessage()` (`lib/utils/res/api_error.dart`).
- **Offline first**: the app writes locally and replays creates, edits, status changes and deletes from an outbox (`OfflineSyncService`). Creates carry a `clientId` so a retried upload returns the existing item instead of a duplicate.
- **Notifications** have no API: reminder alerts, their Done / Not done / Snooze actions and the daily / weekly digests are scheduled on the device (`flutter_local_notifications`). An action is saved locally and synced like any other edit (`/reminders/complete-occurrence`, `/reminders/update-status`, `/reminders/update-reminder`).
